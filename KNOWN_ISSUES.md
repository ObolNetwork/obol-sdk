# Known Issues

This document lists findings that have already been submitted and reviewed for the Obol SDK (`@obolnetwork/obol-sdk`). Every item below has been evaluated by the Obol Security Team and is either resolved, accepted as a design trade-off, or determined not to be a vulnerability.

**Please do not resubmit these findings or close variants of them.** Duplicate submissions will not be eligible for a reward.

The entries describe SDK 3.x (viem, `createObolClient`). Items specific to the 2.x maintenance line (ethers, `Client`) are listed separately at the end.

Many of these findings follow from the SDK's trust model: it is a client library that acts for its caller, with the caller's wallet, against the Obol API and the viem clients the caller passes. Behavior that falls within the assumptions below is not considered a vulnerability. The deployed contracts have their own list in [`obol-splits/KNOWN_ISSUES.md`](https://github.com/ObolNetwork/obol-splits/blob/main/KNOWN_ISSUES.md). Before submitting a report, please review the [bug bounty program](https://docs.obol.org/advanced-and-troubleshooting/security/bug-bounty) scope.

If you believe you have found a new, distinct issue, please report it to the Obol Security Team at [security@obol.tech](mailto:security@obol.tech).

## Trust Model

- **Trust in the Obol API (`api`):** The SDK talks to the Obol API the caller configures (by default the production API; `api.baseUrl` is limited to Obol hosts, plus localhost with `allowLocal`; `api: false` makes the client chain-only) and returns its responses to the caller. Reports that assume a malicious or compromised API are out of scope. Where the SDK acts on API data it checks it locally first: `cluster.accept` verifies the fetched definition (recomputed `config_hash`, fork version, signatures) before signing, `incentives.preflight` / `prepareClaim` check the distributor's code, Merkle root and proof on-chain, `cluster.verifyLock` verifies a lock without trusting the API, and (since 3.0.0-rc.12) `deposits.prepareDeposit` accepts an OVM as Obol-made only from the chain (below). Validator status (`deposits.status` and the writes that read it) is taken from the API as it is, after shape and consistency checks.
- **Trust in the beacon node (`beaconUrl`):** A beacon node the caller passes is trusted for the state it serves, like an RPC. Since 3.0.0-rc.12 the SDK first checks that it is a node of the client's chain (`genesis_validators_root` against the chain table) and in sync (`/eth/v1/node/syncing`: not syncing, `el_offline` not true, not optimistic; `execution_optimistic` answers refused), and fails with `STATUS_UNAVAILABLE` (`beacon_wrong_chain`, `beacon_syncing`, `beacon_optimistic`) otherwise. A node that lies about its genesis root, sync state or registry is a malicious node and out of scope.
- **Trust in the caller's clients and wallet:** The SDK has no RPC endpoints of its own. On-chain reads (contract code checks, address predictions, EIP-1271 signatures through `publicClient` / `publicClients`, withdrawal fees) trust the viem clients the caller passes, and transactions are built for the caller's wallet to sign and send. A malicious RPC or wallet is out of scope.
- **Caller-supplied parameters:** Addresses, recipients, shares, owners and role holders passed to the SDK are the caller's choice. Preparing contracts that pay or are controlled by an address the caller supplied is intended, including SplitV2 and OVM owners who can later change recipients or grant roles.
- **Prepare, then send:** Every write returns a `Prepared` transaction with the checks it ran and a preview; nothing is sent until the caller sends it. A `Prepared` built from state that has since changed (see `blockNumber` and `isStale`) is the caller's to refresh.
- **Findings and acknowledgement (enforced in `send` since 3.0.0-rc.12):** A `prepare*` operation throws for a condition it treats as an error and reports the rest as findings in `Prepared.checks`. `send` refuses (`FINDINGS_NOT_ACKNOWLEDGED`, before the wallet is asked) a `Prepared` with a `severity: 'warning'` finding whose code is not in its `acknowledge` option, and likewise the warnings of a `simulation` passed to it; there is no blanket acknowledgement, and a code that is not a finding code is `PAYLOAD_INVALID`. `info` findings need none. This is enforced only in `send`: a caller that sends `Prepared.request` through its own wallet layer, edits `Prepared.checks`, or acknowledges codes without reviewing them has chosen to, and reports of warnings being "bypassable" that way are out of scope (`findingsToAcknowledge` is exported for such callers). `warningCodes(prepared, simulation)` returns the codes of the warnings a transaction carries, so `send(prepared, { acknowledge: warningCodes(prepared) })` acknowledges them all: that is the intended one-line form for a caller that has shown them (`warningsOf`) to whoever owns the funds, and a caller that uses it without showing them has made that choice. It is computed from the transaction at hand, so it never covers a warning of another transaction.
- **Strict inputs (since 3.0.0-rc.12):** Unknown keys in caller-supplied inputs and options are `PAYLOAD_INVALID` (`unknown_key`), in every `prepare*` input, every options object (`verifyLock`, `isValidLock`, `fromLock`, `assertDepositData`, `status`, `verifyDefinition`, `watch`, `simulate`, `send`, `ovm.getProvenance`, `blsVerify`), the top-level keys of `exits.assertPartialExit` / `exits.aggregate`, and the client config. Documents (cluster definitions and locks, `Deposit` objects, split params, exit wire objects, API and beacon responses) deliberately accept extra fields; reports that an extra field in one of those is not rejected are not vulnerabilities.

## Cluster Definitions & Locks

- **Legacy cluster versions (< v1.10.0):** Reports that v1.6.0 to v1.8.0 definitions or locks have weaker signature coverage. `cluster.prepareDefinition` creates and `cluster.accept` joins only v1.10.0 and later, and the Obol API rejects new definitions and locks below v1.10.0. The SDK still hashes and verifies the older versions so existing clusters stay readable.
- **Cluster version v1.9.0 is unsupported, by design:** The SDK hashes and verifies v1.6.0, v1.7.0, v1.8.0, v1.10.0 and v1.11.0. v1.9.0 definitions and locks (which Charon supports) are not implemented and the Obol API does not accept them. They are reported as unsupported, not as invalid: `cluster.verifyLock` returns `{ ok: false, step: 'hash_mismatch', issue: 'version_unsupported' }` before any other step (first since 3.0.0-rc.12), `isValidLock` is `false`, `computeConfigHash` / `computeDefinitionHash` / `computeLockHash` throw `DEFINITION_INVALID` (`version_unsupported`), `deposits.fromLock` throws `LOCK_INVALID`, and `prepareDefinition` throws `PAYLOAD_INVALID`. Reports that a v1.9.0 file "fails verification" or "cannot be deposited from" are not vulnerabilities.
- **Legacy lock with `partial_deposit_data` — resolved in 3.0.0-rc.12:** Reports that a v1.6.0 / v1.7.0 lock, whose hash and signatures cover only `deposit_data`, verifies with an added `partial_deposit_data` entry and that `deposits.fromLock` returns that unsigned entry. Since rc.12 `cluster.verifyLock` fails such a lock (`deposit_data_invalid`, `partial_deposit_data_unexpected`) at every level, and `deposits.fromLock` throws `LOCK_INVALID` with that issue, also with `verify: false`; legacy locks are read from `deposit_data` only. Before rc.12 the injected entry was returned; `deposits.prepareDeposit` still checked its BLS signature and that its credentials pointed at the expected withdrawal address, so it could change the amount deposited but not the destination. Charon ignores `partial_deposit_data` on legacy locks. The 2.x line has the same extractor and is handled separately.
- **Malformed hex in cluster files:** `computeConfigHash` and the other hash functions hash the strings a definition holds and do not validate every address and hex field (a 19-byte address or a missing `0x` prefix hashes without error). Lock verification and `deposits.fromLock` compare the deposit credentials and pubkeys strictly and fail closed. Not changed in rc.12; tracked for a later release.
- **Unknown options were ignored — resolved in 3.0.0-rc.12:** Reports that `cluster.verifyLock(lock, { level: 'attested', signature: 'all' })` (a misspelt `signatures`) returned `ok: true` without checking any BLS signature. Unknown option keys are now `PAYLOAD_INVALID` (see "Strict inputs"). `level: 'attested'` with the default `signatures: 'none'` still checks no deposit or builder BLS signature; that is its documented meaning, and `deposits.fromLock` passes the validators it returns.
- **`cluster.verifyLock` versus Charon:** `cluster.verifyLock` and `isValidLock` cover the distributed-validator-specs lock checks implemented in the SDK. Charon applies further runtime rules, so a lock that passes here and is rejected by Charon (or a rule enforced only by Charon) is not a vulnerability. Charon is the final gate before a cluster operates. `level: 'attested'` deliberately skips the BLS checks Charon performed in the DKG before the operators signed the lock hash.
- **Lock without partial deposit data:** Reports that a v1.8.0+ lock whose validators have empty or missing `partial_deposit_data` passes verification and that deposits are then taken from `deposit_data`. `cluster.verifyLock` fails such a lock (`deposit_data_invalid`, `deposit_data_missing`), and `deposits.fromLock` verifies the lock first. 2.x accepted it until 2.15.3 (see below).
- **Lock verification cost:** Verifying a large lock is CPU-bound and runs on the calling thread (pure JS by default; the native `@obolnetwork/obol-sdk/blst` backend on Node servers). It yields every `yieldMs` and stops on `signal`, but has no built-in size, time or concurrency limits: those are the responsibility of the service calling it with untrusted input.

## Deposits, OVM & Splits

- **Deploy front-running causing a revert:** A third party can create the same deterministic SplitV2 split first, so the SDK's creation transaction reverts. Funds cannot be redirected this way, and preparing again reuses the existing split (`SPLIT_REUSED`). OVM addresses are read from the factory's `CreateObolValidatorManager` event in the receipt, not predicted.
- **Deposit to a validator that already exists — resolved in 3.0.0-rc.12:** Reports that `deposits.prepareDeposit` with `kind: 'deposit'` returns a sendable transaction for a pubkey that is already a validator, including one registered with someone else's withdrawal credentials (deposit front-running), with only a `DEPOSIT_IS_TOP_UP` warning. Since rc.12, when a status source answers, `kind: 'deposit'` for a pubkey in the validator registry (any status, exited included) always throws: `DEPOSIT_CONFLICT` (`existing: 'validator'`) when its credentials are not `0x01` / `0x02` credentials of the OVM or `expectedWithdrawalAddress` (or are unknown), else `DEPOSIT_VALIDATOR_EXISTS`. `DEPOSIT_IS_TOP_UP` no longer exists. A queued deposit with other credentials throws `DEPOSIT_CONFLICT` (`existing: 'queued'`) as before.
- **Deposit without a status source:** With `api: false` and no `beaconUrl` (or an Obol API without the deposit-status route and no `lockHash` / `beaconUrl`) the existence checks above cannot run. `prepareDeposit` then adds `DEPOSIT_EXISTENCE_UNCHECKED`, which since 3.0.0-rc.12 is a warning that `send` refuses until acknowledged. A caller that acknowledges it has taken on the check.
- **Top-up to a validator with other credentials:** `kind: 'topUp'` to a validator whose credentials do not point at the OVM or `expectedWithdrawalAddress` is allowed (a top-up may be a deliberate donation) and carries the warning `TOP_UP_CREDENTIALS_FOREIGN` (since 3.0.0-rc.12), which `send` refuses until acknowledged.
- **Beacon fallback returned "new" for every pubkey — resolved in 3.0.0-rc.12:** Reports that `deposits.status` (and so `prepareDeposit`) treated every pubkey as `new` when `beaconUrl` pointed at a node of another network or one still syncing, and that any Obol API error (400, 401, 429, ...) switched the source to the beacon node. Since rc.12 the node is checked first (see "Trust in the beacon node") and the fallback happens only when the API is unavailable: `API_TIMEOUT`, or `API_ERROR` with no HTTP status or a 5xx. A 400, 401, 403, 409, 422, 429 or 451 is thrown. A 404 from `POST /v1/validators/:network/deposit-status` means that API deployment has no such route (the route answers `new`, never 404, for an unknown pubkey) and the next source is used; a 404 for an unknown `lockHash` is thrown.
- **OVM provenance from the Obol API — resolved in 3.0.0-rc.12:** Reports that `ovm.getProvenance` returns `obol` on the API's word and that `prepareDeposit` relies on it. Since rc.12 an API `obol` answer is confirmed against the creation receipt (a successful transaction with the chain table factory's `CreateObolValidatorManager` log for the address) and then returned as `source: 'chain'`; when it cannot be confirmed the result is `source: 'api'` and its reason says so. `deposits.prepareDeposit` requires chain confirmation (`requireChain`: the receipt, else the factory log scan) and throws `OVM_NOT_OBOL` / `PROVENANCE_UNKNOWN` otherwise. Other OVM writes (`prepareWithdraw`, `prepareConsolidate`, role writes, distributions) still accept `obol` / `api`: they act on a contract the sender already holds a role on and send no new principal to it.
- **Consolidation into another withdrawal address:** `ovm.prepareConsolidate` allows a target whose withdrawal address differs from the source's (the beacon chain allows it) and reports it as the warning `CONSOLIDATION_CREDENTIALS_DIFFER`, which `send` refuses until acknowledged (since 3.0.0-rc.12; before, a flag `acknowledgeStakeMovesToTarget` was required on every call, whether stake moved or not). When the addresses could not be compared (no status source, credentials not reported) the warning is `VALIDATOR_STATUS_UNCHECKED`.
- **Unusable split recipients — resolved in 3.0.0-rc.12:** Reports that the zero address (or the SplitsWarehouse, a factory, or the split itself) is accepted as a split recipient, permanently locking that share, and that `distributor: 0x0` is accepted with a distribution incentive. Since rc.12 `splits.splitParams` and the presets refuse the zero address (`zero_address`); `splits.prepareCreateSplit`, `setup.prepareOvmWithSplits` and the presets refuse the chain's protocol contracts (`protocol_contract`: Warehouse, PullSplit factory, OVM factory, SplitMain, OWR factory, batch deposit, beacon deposit contract, EIP-7002 / EIP-7251 request contracts, Obol token), and the first two also the split's own predicted address (`self_recipient`); `splits.prepareDistributeAll` refuses a zero `distributor` when a split has an incentive. Any other recipient is the caller's choice (see "Caller-supplied parameters"); `splits.predictSplit`, `getSplit` and `prepareDistributeAll` do not apply these rules to splits that already exist. OVM recipients (`setup.prepareCreateOvm`) are checked for the zero address and public forwarders only.
- **Top-up deposits skip BLS verification:** With `kind: 'topUp'`, `deposits.assertDepositData` and `deposits.prepareDeposit` do not verify deposit signatures, because top-ups to existing validators do not need them. The caller asserts each deposit is a top-up; under the default `kind: 'deposit'`, a deposit with an all-zero signature is refused (`DEPOSIT_LOOKS_LIKE_TOP_UP`).
- **Simulation is advisory and experimental:** `experimental.simulate` trusts the node it runs on and is not a security boundary. Since 3.0.0-rc.12 it does not fail open: a failed before / after read is the warning `SIMULATION_READS_INCOMPLETE`, `matchesPreview.ok` is true only for `status: 'match'` (never when nothing was compared or a read failed), and a node that cannot simulate gives the warning `SIMULATION_UNAVAILABLE`; `send(prepared, { simulation })` refuses those until acknowledged. Reports that a malicious RPC can make a simulation look clean are out of scope (trust in the caller's clients).
- **Exit epoch cannot change while an exit is stored:** `exits.assertPartialExit` rejects a partial exit whose epoch differs from the stored exit's, higher or lower (`EXIT_EPOCH_MISMATCH`, with `direction` since 3.0.0-rc.12); 2.x accepted a higher epoch. Partial signatures over different epochs cannot be aggregated. Re-signing at another epoch requires the stored exit to be deleted first, which the Obol API provides per operator (`charon exit delete`: each operator removes its own partial, and the document goes when none is left); the API has no whole-document delete. This is an operational constraint, not a vulnerability.
- **Gnosis and Sepolia:** These chains are accepted for cluster files and terms only. Contract operations throw `UNSUPPORTED_CHAIN` there (except `experimental.legacy.getOwrTranches`, which only reads an existing OWR).

## Terms and Conditions

- **Terms and conditions signature has no chain ID:** The EIP-712 signature that `terms.accept` (2.x: `acceptObolLatestTermsAndConditions`) creates to accept Obol's terms and conditions uses a domain with only `name` and `version`, and no `chainId`. This is deliberate: the terms are the same on every network, so one acceptance by an address covers all of them. The Obol API stores one acceptance per address and terms version, and re-submitting an accepted one changes nothing. The `fork_version` sent with it only selects the chain on which a contract wallet (ERC-1271) signature is checked. The API does not serve the signature back: `GET /v1/termsAndConditions/{address}` returns only whether the address has accepted. Replaying the signature, on another network or by another party, can only record an acceptance its signer already gave.

## Runtime & Packaging

- **`Buffer` in the browser build — resolved in 3.0.0-rc.12:** Reports that in a browser without a `Buffer` polyfill (Vite, Rollup, esbuild, workers, edge runtimes) `cluster.computeConfigHash` threw and `cluster.verifyLock` reported a valid lock as `hash_mismatch`. Neither `src/` nor the SSZ list hashing it uses needs `Buffer` since rc.12 (`@chainsafe/ssz` 0.14.3's `mixInLength` did; the SDK's list types replace that step). `no-restricted-globals` in `.eslintrc.js` and `test/package/browserNoBuffer.spec.ts` (the built browser bundle run without `Buffer` on Charon-made locks) keep it so.
- **`isObolError` across module copies — resolved in 3.0.0-rc.12:** `isObolError` checks a `Symbol.for('@obolnetwork/obol-sdk.ObolError')` brand and a string `code`, so an error thrown by the CommonJS build is recognised by the ESM build and by another installed version. `error instanceof ObolError` remains copy-specific, as for any class; use `isObolError`. An object that forges the brand is treated as an `ObolError`, which grants nothing.
- **Internal exceptions inside `verifyLock` become step failures:** A step that throws something other than its own failure (a bug, an environment problem) is reported as that step failing, so `verifyLock` fails closed with a step name rather than an exception. Not changed in rc.12.

## SDK 2.x

- **SplitMain split address front-running (`createObolRewardsSplit` / `createObolTotalSplit`) — resolved in 2.15.2:** Reports that the SDK freezes a predicted SplitMain address as an OWR reward recipient and that a front-run `createSplit` diverts rewards. Immutable splits (no `controllerAddress`, the default) have a deterministic address over their recipients and fees, so a front-run can only deploy the same split or cause a revert. For mutable splits (with a `controllerAddress`), 2.15.2 no longer predicts an address: it deploys the split first and uses the address from its `CreateSplit` event. SDK 3.x does not create SplitMain or OWR contracts.
- **Lock without partial deposit data — resolved in 2.15.3:** Before 2.15.3, `validateClusterLock` accepted a v1.8.0+ lock whose validators had empty or missing `partial_deposit_data` (with `deposit_amounts: null`), and `getDepositData` then used the validator's `deposit_data`, which lock verification does not cover for those versions. Building such a lock needs the cluster's own operators (a solo creator or a colluding threshold).
- **Same-epoch exit treated as already processed (`validateExitBlobs`) — resolved in 2.15.3:** A same-epoch blob was skipped as already processed when the stored data held no signature from this operator. No security impact: the helper does not broadcast, recombination rejects duplicate share indices and the beacon node verifies the aggregate.
- **Trust model:** 2.x follows the same model with its own names: the configured `baseUrl`, the ethers provider and signer (including `safeRpcUrl` for Safe signature checks), and the beacon node URL passed for exit validation.
