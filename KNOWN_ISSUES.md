# Known Issues

This document lists findings that have already been submitted and reviewed for the Obol SDK (`@obolnetwork/obol-sdk`). Every item below has been evaluated by the Obol Security Team and is either resolved, accepted as a design trade-off, or determined not to be a vulnerability.

**Please do not resubmit these findings or close variants of them.** Duplicate submissions will not be eligible for a reward.

Many of these findings follow from the SDK's trust model: it is a client library that acts for its caller, with the caller's signer, against the Obol API and RPC endpoints the caller chooses. Behavior that falls within the assumptions below is not considered a vulnerability. The deployed contracts have their own list in [`obol-splits/KNOWN_ISSUES.md`](https://github.com/ObolNetwork/obol-splits/blob/main/KNOWN_ISSUES.md). Before submitting a report, please review the [bug bounty program](https://docs.obol.org/advanced-and-troubleshooting/security/bug-bounty) scope.

If you believe you have found a new, distinct issue, please report it to the Obol Security Team at [security@obol.tech](mailto:security@obol.tech).

## Trust Model

* **Trust in the configured Obol API (`baseUrl`):** The SDK talks to the API the caller configures (by default the production Obol API) and returns its responses to the caller. Reports that assume a malicious or compromised API, or a caller who points the SDK at one, are out of scope. Where the SDK acts on API data it checks it locally first: `acceptClusterDefinition` recomputes the `config_hash` and checks the network before signing, `claimIncentives` checks that the distributor's deployed bytecode and token are the expected ones and that the Merkle proof matches the root stored in that contract, and `validateClusterLock` verifies a lock without trusting the API.
* **Trust in the configured RPC, beacon node and signer:** On-chain reads (contract checks, address predictions, Safe signature checks via `safeRpcUrl`, withdrawal fees) and beacon node reads (the genesis validators root that `validateExitBlobs` uses) trust the endpoints the caller provides, and transactions are signed by the caller's signer. A malicious RPC, beacon node or wallet is out of scope.
* **Caller-supplied parameters:** Addresses, recipients, percentages, controllers and owners passed to the SDK are the caller's choice. Deploying contracts that pay or are controlled by an address the caller supplied is intended, including mutable splits (`controllerAddress`) and SplitV2 / OVM owners who can later change recipients. The Obol Retroactive Funding recipient is appended to splits by design.

## Cluster Definitions & Locks

* **Legacy cluster versions (< v1.10.0):** Reports that legacy (v1.6.0 to v1.8.0) definitions or locks can be created or accepted with weaker signature coverage. The SDK no longer creates or joins definitions below v1.10.0 (`MIN_SUPPORTED_CLUSTER_VERSION`), and the Obol API rejects them for new clusters. Existing legacy locks still hash and validate so running clusters keep working. A legacy lock that the Obol API returns with `definition_stored: false` is an exception: the API stored it before it kept each lock's own definition and serves the definition record for its `config_hash` instead, which can differ (for example, without operator ENRs and signatures), so the lock hash does not match and `validateClusterLock` returns `false`. Validate such a lock from its original lock file.
* **`validateClusterLock` versus Charon:** `validateClusterLock` covers the cryptographic and structural checks implemented in the SDK. Charon applies further runtime rules, so a lock that passes here and is rejected by Charon (or a rule enforced only by Charon) is not a vulnerability. Charon is the final gate before a cluster operates.
* **Lock without partial deposit data falling back to `deposit_data` — resolved:** Reports that a v1.8.0+ lock whose validators have an empty or missing `partial_deposit_data` (with `deposit_amounts: null`) passed `validateClusterLock`, after which `getDepositData` / `depositDataFromLock` used the validator's `deposit_data`, which lock verification does not cover for these versions. Building such a lock needs the cluster's own operators (a solo creator or a colluding threshold). Since 2.15.3 (and in 3.0), validation rejects a v1.8.0+ validator without partial deposit data, and `deposit_data` is only read from locks before v1.8.0.
* **`partial_deposit_data` on a lock before v1.8.0 — resolved:** Reports that a `partial_deposit_data` entry added to a v1.6.0 or v1.7.0 lock was returned by `getDepositData` / `depositDataFromLock` in place of the lock's `deposit_data`, while `validateClusterLock` still passed. Locks before v1.8.0 hash and sign `deposit_data` only, so the added entry needed no signing key, only control of the lock JSON being loaded. Since 2.16.1, `validateClusterLock` rejects a lock before v1.8.0 whose validators carry a non-empty `partial_deposit_data`, and the deposit helpers read exactly one field per version, also with `verify: false`: `deposit_data` before v1.8.0, `partial_deposit_data` from v1.8.0. Charon ignores `partial_deposit_data` on these locks.
* **Lock validation cost:** Validating a large lock is CPU-bound (about a minute for 1,000 validators), so an untrusted lock can occupy a CPU. The SDK limits this in Node: validation runs in worker threads where available, at most 2 validations run at once per process (`OBOL_SDK_MAX_CONCURRENT_LOCK_VALIDATIONS`; further calls throw `ClusterLockValidationBusyError`), and a run is stopped with `ClusterLockValidationTimeoutError` after 300 seconds. The SDK does not limit the size of a lock or the rate of calls: a service that validates untrusted locks must do that itself.

## Exits

* **`recombineExitBlobs` returning an invalid exit signature — resolved:** Reports that `client.exit.recombineExitBlobs` returns a signature it never checked, so too few partial signatures, an invalid partial signature, or partials for another network give back an invalid exit without an error. Since 2.16.0 every call verifies the aggregated signature against `exitBlob.public_key` for the exit message (`epoch`, `validator_index`) before returning, and throws `ExitRecombineError` when it does not verify. This happens with and without the `options` argument, and no option turns it off. The signing domain comes from constants for the client's `chainId` (`EXIT_NETWORKS` in `src/constants.ts`: the Capella fork version and genesis validators root of Mainnet, Hoodi, Sepolia and Gnosis), so no beacon node is needed or trusted. An `Exit` constructed directly for a chain without constants throws `UnsupportedChainError` unless `options` supply the fork version and genesis validators root, and the result is verified with those. Versions before 2.16.0 returned the aggregate unchecked; the fix is to upgrade.
* **What `recombineExitBlobs` does not check:** A returned exit is a valid BLS signature by `public_key` over that `epoch` and `validator_index` on the client's chain. The following are outside the method by design and are not vulnerabilities:
    * It does not check that `validator_index` is the beacon chain index of `public_key`, or that `epoch` has been reached. That needs beacon state; the beacon chain rejects an exit where either is wrong.
    * Without `options.clusterConfig` it does not check each partial signature separately or compare their number with a threshold. Neither is needed for safety: an aggregate built from fewer than the threshold of valid partials, or including an invalid one, does not verify and is refused. The cost is that one invalid stored partial makes the call fail until `clusterConfig` is passed, which verifies each partial against its public share, leaves invalid ones out and names them in the error.
    * With `options.clusterConfig`, the public shares and threshold are the caller's. Wrong shares can only make the call fail, because the aggregate is still verified against `public_key`.
    * `options.genesisValidatorsRoot` and `options.beaconNodeApiUrl` cannot change the signing domain on a chain with constants. A value that differs from the chain's is refused with `InvalidArgumentError`.
* **Exit helpers do not submit anything:** `client.exit.validateExitBlobs` and `recombineExitBlobs` return data to the caller and send nothing to the Obol API or a beacon node. They are not the enforcement point for exits: the Obol API and Charon run their own checks on partial exits, and the beacon chain verifies the signed exit. A cluster operator who submits partial exits for a different epoch than the other operators delays that validator's exit for their own cluster only, and the cluster undoes it with `charon exit delete`.
* **`validateExitBlobs` inputs:** `validateExitBlobs` verifies the operator's payload signature and each partial signature against the `clusterConfig` and `existingBlobData` the caller passes, with the genesis validators root from the beacon node the caller passes. It does not fetch or authenticate any of them; a caller that passes a cluster, stored exit or beacon node it does not trust is outside the trust model above.
* **Exit epoch and validator index parsing — resolved:** Reports that exit `epoch` and `validator_index` strings were parsed with `BigInt()`, which also accepts hexadecimal, surrounding whitespace and an empty string, and were then hashed as JavaScript numbers, so values above 2^53 - 1 were rounded (an exit for epoch 2^64 - 1 hashed like epoch 0). Since 2.16.0 all exit methods accept only decimal digits up to 2^64 - 1 (`InvalidArgumentError` otherwise) and hash the exact 64-bit value. Leading zeros are still accepted; `recombineExitBlobs` returns the values without them.
* **Same-epoch exit treated as already processed — resolved:** Reports that `validateExitBlobs` skipped an exit blob as already processed when stored data existed for the same validator and epoch but held no signature from this operator. A skipped blob was left out of the returned list without being verified; it was never returned as valid, so the effect was a delayed exit, not an accepted invalid signature. Since 2.15.3 such a blob is verified like a new one.

## Terms and Conditions

* **Terms and conditions signature has no chain ID:** The EIP-712 signature that `acceptObolLatestTermsAndConditions` creates to accept Obol's terms and conditions uses a domain with only `name` and `version`, and no `chainId`. This is deliberate: the terms are the same on every network, so one acceptance by an address covers all of them. The Obol API stores one acceptance per address and terms version, and re-submitting an accepted one changes nothing. The `fork_version` sent with it only selects the chain on which a contract wallet (ERC-1271) signature is checked. The API does not serve the signature back: `GET /v1/termsAndConditions/{address}` returns only whether the address has accepted. Replaying the signature, on another network or by another party, can only record an acceptance its signer already gave.

## Splits & Deployments

* **SplitMain split address front-running (`createObolRewardsSplit` / `createObolTotalSplit`) — resolved:** Reports that the SDK freezes a predicted SplitMain address as an OWR reward recipient and that a front-run `createSplit` diverts rewards. Immutable splits (no `controllerAddress`, the default) have a deterministic address over their recipients and fees, so a front-run can only deploy the same split or cause a revert. For mutable splits (with a `controllerAddress`), whose address depends on SplitMain's nonce, the SDK since 2.15.2 no longer predicts an address: it deploys the split first and uses the address from its `CreateSplit` event. Both methods are deprecated in favor of the OVM and SplitV2 methods, whose split addresses are deterministic.
* **Deploy front-running causing a revert:** Immutable SplitMain splits and SplitV2 splits have deterministic addresses, so a third party can deploy the same split first and make the SDK's deployment transaction revert. Funds cannot be redirected this way: the address commits to the recipients, and the contract a third party deploys there is the same one. Re-running the method finds the split already deployed and reuses it. OVM and OWR contracts are not deployed at a predicted address (each call deploys a new one), so they cannot be front-run this way.
* **Top-up deposits skip BLS verification:** With `kind: 'topUp'`, `eoa.deposit` and `splits.deposit` do not verify deposit signatures, because the beacon chain ignores the signature of a deposit to an existing validator. The caller asserts each deposit is a top-up; if the validator does not exist, a deposit with an invalid signature is lost, which is the caller's responsibility under this option. The default is `kind: 'deposit'`, which verifies every signature and refuses a deposit with an all-zero signature (`DEPOSIT_LOOKS_LIKE_TOP_UP`), so a top-up is never sent unverified by accident.
* **Gnosis and Sepolia:** These chains are accepted for cluster definitions, locks and the exit helpers only. Splitter and EOA contract methods throw `UnsupportedChainError` there, and `claimIncentives` fails its pre-flight check (`UNSUPPORTED_CHAIN`), in each case before a transaction is sent.
